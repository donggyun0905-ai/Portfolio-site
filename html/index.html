MAIN PROJECT 2026

메인 프로젝트

Dativus

보안과 비용을 동시에 잡은 "팀 전용 AI 팀원" 플랫폼

기간 : 2026.03 — 2026.06 (15주) 역할 : 팀 프로젝트 (3인, 팀장) → 이후 개인 레포로 Fork하여 단독 고도화 진행 중
FastAPILangGraphSpring BootPostgreSQLChromaDBNeo4jDocker
PROBLEM + ARCHITECTURE

단일 LLM 챗봇은 전문성 부족(불만족 사유 75.6%)과 개인화 맥락 유지의 어려움이라는 한계가 뚜렷했고, 퍼블릭 AI 사용 시 사내 기밀 유출 위험도 컸음. Spring Boot(비즈니스 로직)와 FastAPI(AI 코어·SSE 스트리밍)로 서버를 이원화하고, Cloudflare Tunnel + AWS API Gateway로 Zero-Trust 네트워크를 구성.

KEY DECISIONS
  • MSA 이원화 — 단일 Spring Boot로 SSE를 처리하면 Java 블로킹 I/O 특성상 동시 접속자 증가 시 가용성이 급격히 저하되어, 일반 REST는 Spring Boot(블로킹, 트랜잭션 강점) / AI 추론·SSE는 FastAPI(asyncio 논블로킹)로 역할 분리
  • LangGraph 채택 — 에이전트 간 상태를 그래프 노드/엣지로 명시적으로 관리해 Recursion Limit 기반 Deadlock 방지와 조건부 분기가 가능. AutoGen/CrewAI 대비 상태 전이 제어 유연성이 높고 FastAPI 비동기 환경과 통합이 용이
  • ChromaDB 채택 — Pinecone/Weaviate 같은 상용 서비스 대신, 온프레미스 설치로 벡터 데이터 외부 유출 위험 제거 + Python 네이티브 통합 + 무료 오픈소스(운영비 0원)라는 이유로 선택
TROUBLESHOOTING + 성과
  • 에이전트 간 자가 검증 루프에서 판단 기준이 충돌해 무한 루프(Deadlock) 발생 → LangGraph의 Recursion Limit으로 검증 순환을 최대 3회로 제한, 초과 시 Safety-Fallthrough 모드로 자동 전환해 강제 응답 송출
  • Groq API 무료 플랜의 분당 호출 한도 초과로 429 에러 빈발(특히 멀티에이전트 병렬 팬아웃 구간) → 지수 백오프(1→2→4초) 재시도 후 로컬 Ollama(Llama-3)로 자동 Fallback 전환해 서비스 중단 방지

헬스케어 (DeepStream)

AI·헬스데이터 기반 어르신 맞춤형 건강관리 서비스

기간 : 2025.09 — 2025.12 (15주) 역할 : 웨어러블 앱 & 서버 구축, 사용자 건강데이터 입력/저장 기능 구현, 복약관리(알약 사진인식·DB저장) 구현 · 팀장
AndroidHealth ConnectFastAPICNNGemini APIPostgreSQL
BACKGROUND

고령층은 복합 만성질환으로 지속 모니터링이 필요하지만(노인의 33%), 65세 이상의 25%가 연 1회 이상 낙상을 경험하고 약물 이상반응의 1/3은 예방 가능함에도 관리가 부재한 상황. 웨어러블·Health Connect·AI를 결합해 실시간 건강 모니터링과 보호자 공유 체계를 구축하고자 시작.

DESIGN DECISIONS + RESULT
  • AI 약품 인식 — 알약 촬영 → CNN 기반 분류 → 식약처 공공 API 연동으로 성분·효능 제공
  • 헬스데이터 엔지니어링 — 스마트워치(Galaxy Watch 5) → Health Connect → Android 브릿지 앱(Retrofit) → FastAPI Ingest Server ETL 저장
  • 맞춤형 건강 조언 — Gemini API 기반 생성형 AI + RAG로 최근 n일 데이터를 분석해 개인화된 조언 생성
  • 보호자 연동 — 실시간 데이터 공유 및 위험 상황 알림

결과 : 웨어러블 → Health Connect → FastAPI로 이어지는 실시간 헬스데이터 수집 파이프라인 구축, 실제 웨어러블 데이터 기반 통합 기능 검증 완료

처음 프로젝트

맑은 출근길 (Nice Commuting Day)

기간 : 2025.04 — 2025.06 (9주) 역할 : 로그인/사용자 등록, 메인화면 제작·디자인, 날씨별 옷차림 안내(기상청 API) 구현 · 팀장 (3인) 사용 데이터 : 기상청, 한국환경공단 에어코리아, 부산광역시 버스정보시스템 공공데이터 기술 : Java, Swing, NetBeans, RESTful API(XML 파싱)
계기

바쁜 출근길에 날씨·미세먼지·버스 정보가 여러 플랫폼에 흩어져 있어 매번 따로 확인해야 하는 불편함을 해결하고 싶어서 시작한, 제 첫 팀 프로젝트입니다.

핵심 기술 선택 이유

기상청·에어코리아 API는 30분~1시간 단위로만 갱신되어 실시간성 요구와 어긋나는 문제가 있어, 갱신 전 데이터를 임시로 캐싱해 두는 방식으로 해결했습니다. 또한 버스 도착 정보 조회 시 출발·도착 정류장 쌍으로 최단 경로를 탐색하면 지연이 컸는데, 정류장 + 노선 번호만으로 조회하는 방식으로 바꿔 응답 속도를 개선했습니다. API가 제공하는 원시 값(T1H, WSD, REH)만으로는 부족해 체감온도·이슬점 계산 로직을 직접 구현해 사용자에게 더 유용한 지표로 가공했습니다.

결과 · 배운 점

기능 구현률 95%, 설계-구현 일치도 90%, 성능 95%를 달성했습니다. 처음으로 공공 API 연동과 서버-클라이언트 구조를 직접 설계해본 경험이었고, 이때 배운 실시간 데이터 파이프라인의 감각이 이후 Dativus의 하이브리드 라우팅 설계로 이어졌습니다.
